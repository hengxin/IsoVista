# 07 · Bug Reducer 方案

## 1. 设计目标

把平台发现的"原始 bug case"（raw case，动辄数万操作、十余线程）加工为**可提交、可复现、不重复**的工单素材，直接对标 Pisco（R11）的三准则：

| 准则 | 含义 | 平台指标 |
|---|---|---|
| **可复现（Reproducibility）** | 指定精确操作顺序，bug 确定性复现 | 复现率 >94%（R11 统计先验） |
| **简洁（Conciseness）** | 最小事务集（通常 <4 事务、8–10 操作） | 归约后操作数下降 ≥90% |
| **唯一（Uniqueness）** | 与已报告 bug 不重复 | 去重准确率 ≥90%（R11：91.6%） |

## 2. 总体流程

```
Checker 输出 raw case（历史 + 反例环）
   │
   ▼
① 执行序推断（确定性复现）── 内部状态镜像（版本链/锁表）+ 冲突操作批排序
   │
   ▼
② 依赖感知归约（最小化）── divide-and-conquer，保 bug 触发操作
   │
   ▼
③ 去重（唯一性）── 粗筛 + 精排 + 人工复核队列
   │
   ▼
④ 产出：最小复现脚本（可执行 SQL/操作序列）+ 归约报告 + bug 库记录
```

## 3. ① 执行序推断与确定性复现

**问题**：客户端 trace 只有时间区间，并发操作大量重叠；直接重放不保证复现。

**方案（R11 的内部状态镜像法）**：

1. 镜像 DBMS 内部状态（按主流协议建模）：
   - MVCC：版本链（每对象版本序）；
   - 2PL/S2PL：锁表与锁持有/等待；
   - OCC：提交校验集；
   - TO/Percolator：时间戳分配器；
2. 用并发控制协议模拟原始场景中冲突操作的调度（加锁/释放、可见版本检索），推出一个**可行的服务端执行序**；
3. 构造**操作批序列**：冲突操作分入不同批（批内可并行、批间定序），重放时按批并行执行；
4. 重放验证：在目标 DBMS 上执行该顺序，确认 bug 仍触发；否则回退到枚举兜底（限定预算）。

**平台落地**：`OrderInferencer` 组件 + `ReplayRunner`（复用 Executor 的协同原语，04 §6）。对无法建模协议的 DBMS，退化为"区间重叠约束 + 枚举"（限定组合数，R11 指出纯枚举有组合爆炸风险）。

## 4. ② 依赖感知归约（最小化）

**问题**：delta debugging（DDMin/C-Reduce）按操作集合均匀划分，忽视操作间依赖，试错次数多（R11：Pisco 仅用其 20%/33.3% 的时间）。

**方案（R11 的依赖感知 divide-and-conquer）**：

1. **归约单元构造**：按事务/会话/冲突对把操作聚为"归约单元"（删除单元不破坏语法与基本依赖）；
2. **递归归约**：对每个单元尝试删除 → 重放验证（借助 ① 的确定性复现，验证从"概率性"变为"确定性"，大幅减少重复）；
3. **依赖约束**：从事务依赖图推导"不可删"操作集（如反例环上的核心操作、wr 匹配的写操作），优先保语义、避免无效尝试；
4. **终止**：无法再删任何单元而保持 bug 触发。

**平台落地**：`CaseReducer` 组件，归约过程全程记录（每次删除的验证结果），产出归约报告（删除率、验证次数、耗时）——这本身就是 checker/数据库研究的素材。

## 5. ③ 去重（唯一性）

**问题**：同一 bug 的不同 raw case 表象迥然（MySQL 官方数据：平均 114 天/报告的人工查重，R11）。

**方案（R11 的领域知识驱动多 agent 框架，平台实现为规则 + 模型混合）**：

1. **规范化指纹**：对最小 case 提取结构指纹（事务数、操作类型序列、冲突图拓扑、异常类型、隔离级别、DBMS 版本）；
2. **粗筛**：指纹 + 异常类型 + DBMS 大版本过滤候选集；
3. **精排**：候选 case 两两比对（反例环同构、wr 模式匹配、操作语义等价类）；
4. **人工复核队列**：模型判定不确定的进入队列（平台 UI 支持一键确认/驳回，并回流为标注数据）。

**平台落地**：`BugDeduplicator` + bug 库（见 §7）。

## 6. 与平台其他模块的联动

| 模块 | 联动 |
|---|---|
| Checkers（06） | 消费 counterexample 作为 raw case；去重前先跑交叉验证确保 bug 高置信 |
| Executor/Logger（04） | 重放验证复用执行通道与协同原语 |
| Synthesizer（05） | `crop-to-cycle`/`project` 变换是归约的底层原语；合成最小反例（05 §4.3）用于归约结果的自检 |
| Benchmark（02） | `regression/` 目录由归约后的最小 case 自动填充（可执行复现脚本） |
| 可视化（08） | 归约前后 case 并排展示（raw → minimal 的 diff 视图） |

## 7. Bug 库（平台资产）

```
bug_store/
├── <bug_id>/
│   ├── raw_case.{json,txt}        # 原始历史 + 反例
│   ├── minimal_case.{sql,txt}     # 最小复现脚本（可直接执行）
│   ├── reproduce_order.json       # 操作批序列（确定性复现）
│   ├── reduction_report.json      # 归约统计
│   ├── fingerprint.json           # 结构指纹
│   ├── metadata.json              # DBMS/版本/隔离级别/异常类型/发现时间/标签(Open-Fixed)
│   └── graphs/{raw,minimal}.dot   # 可视化
```

- 与现有 `BugStore`（后端）合并：现有按 run 扫描的 bug 表扩展为持久化 bug 库；
- 支持导出（zip/JSON）与公开数据集发布（R11 同样开源了 bug case 数据集）；
- 标签体系：`Open/Fixed/Verified/Duplicate/Wontfix`（现有前端已有 Open/Fixed 标签，扩展之）。

## 8. 验收要点

1. 对平台标准负载集发现的 bug，归约后中位操作数下降 ≥90%，复现率 ≥94%；
2. 归约耗时不超过 DDMin 基线的 1/3（对标 R11）；
3. 去重在内部标注集上准确率 ≥90%，且全部唯一 bug 提交后 2 个工作日内被社区接受（过程指标）；
4. `regression/` benchmark 中每个已知 bug 都有可一键执行的最小复现脚本。
